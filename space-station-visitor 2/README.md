# Space Station Visitor

Индивидуальное задание №6 по Software Design Patterns: реализация Visitor на Java.

В проекте я использую модули космической станции. Одну коллекцию модулей обрабатывают разные посетители: расчётом суточной потребности в энергии, планированием обслуживания и формированием инвентарного отчёта. Числа и интервалы условные и служат учебной моделью.

## Запуск

Нужен JDK 17 или новее. Сторонних библиотек, Maven и доступа к интернету не требуется.

macOS / Linux, из папки проекта:

```sh
sh run.sh
sh run-tests.sh
```

Windows PowerShell, из папки проекта:

```powershell
New-Item -ItemType Directory -Force build | Out-Null
javac --release 17 -encoding UTF-8 -d build src/station/*.java
java -cp build station.Main
javac --release 17 -encoding UTF-8 -d build src/station/*.java tests/station/*.java
java -cp build station.VisitorTests
```

## Компоненты паттерна

| Роль | Реализация |
| --- | --- |
| Element | `StationModule`, объявляет `accept(ModuleVisitor)` |
| Concrete Elements | `HabitatModule`, `LaboratoryModule`, `GreenhouseModule` |
| Visitor | `ModuleVisitor`, объявляет метод для каждого типа модуля |
| Concrete Visitors | `EnergyConsumptionVisitor`, `MaintenanceVisitor`, `InventoryReportVisitor` |
| Object Structure | `List<StationModule>` в `Main` |
| Client | `Main`, создаёт объекты и обходит коллекцию |

Каждый элемент — неизменяемый Java record. Он хранит данные, проверяет их корректность и принимает посетителя. Алгоритмы вынесены в отдельные классы посетителей.

## Double dispatch

Пример для жилого модуля:

```java
StationModule module = new HabitatModule("Orion", 4, 35);
ModuleVisitor visitor = new EnergyConsumptionVisitor();
module.accept(visitor);
```

1. Во время выполнения Java выбирает `HabitatModule.accept`, исходя из реального типа элемента.
2. Внутри него вызывается `visitor.visitHabitat(this)`. Здесь `this` имеет конкретный тип `HabitatModule`.
3. Java выбирает реализацию `visitHabitat` у реального посетителя — `EnergyConsumptionVisitor`.

Итоговое поведение зависит от двух объектов: типа элемента и типа посетителя. Имена `visitHabitat`, `visitLaboratory`, `visitGreenhouse` явно различают типы, поэтому проверять их через `instanceof` не нужно.

## Алгоритмы и ожидаемый результат

- Жилой модуль: 20 кВт·ч базовой нагрузки плюс 5 кВт·ч на жителя в сутки.
- Лаборатория: 12 кВт·ч на активный эксперимент в сутки.
- Оранжерея: 8 кВт·ч на стеллаж в сутки.
- Обслуживание необходимо начиная с 30, 14 и 7 дней соответственно.

Для Orion с 4 жителями, Kepler с 3 экспериментами и Eden с 6 стеллажами: `20 + 4 × 5 + 3 × 12 + 6 × 8 = 124 кВт·ч`.

```text
SPACE STATION MODULES
Habitat Orion: residents = 4
Laboratory Kepler: active experiments = 3
Greenhouse Eden: growing racks = 6
Daily energy demand: 124 kWh
Maintenance tasks:
Orion: inspect air filters
Eden: clean irrigation system
```

Посетители накапливают результат одного обхода. Для нового независимого расчёта создаётся новый экземпляр посетителя. Повторный обход тем же экземпляром добавит результаты ещё раз.

## Пять принципов Clean Code

1. **Понятные имена.** `EnergyConsumptionVisitor`, `daysSinceService`, `activeExperiments` объясняют назначение класса или значения. Суффиксы `Module` и `Visitor` различают роли элементов и операций.
2. **Полиморфизм вместо проверок типов.** `Main` работает через `StationModule`, а каждый `accept` направляет вызов в подходящий метод посетителя. В исходниках нет цепочек проверок типов и приведений типов.
3. **Single Responsibility Principle.** Каждый посетитель реализует одну операцию для всех типов модулей: энергию, обслуживание или отчёт. Вывод результатов делает клиент `Main`.
4. **Инкапсуляция.** Records содержат приватные final-поля и предоставляют только чтение. Посетители используют минимальные данные через accessors, без сеттеров. Списки результатов возвращаются через `List.copyOf`. Компромисс Visitor: операции должны знать данные элементов; здесь раскрываются только необходимые свойства предметной области, а не изменяемое внутреннее состояние.
5. **Open/Closed Principle для новых операций.** `InventoryReportVisitor` демонстрирует третью операцию. Для её добавления достаточно нового класса, реализующего существующий `ModuleVisitor`, и подключения в клиенте. Интерфейс посетителя и классы элементов менять не требуется.

Дополнительно: числовые коэффициенты и интервалы имеют именованные константы; общая валидация вынесена в `Validation`; некорректные данные отклоняются при создании объекта.

## Расширяемость и ограничения

Для четвёртой операции нужен новый класс, реализующий `ModuleVisitor`. В нём должны быть все три метода посещения. Затем новый посетитель подключается в `Main`. Существующие элементы и посетители менять не нужно.

Добавление нового **типа элемента** дороже: потребуется добавить метод в `ModuleVisitor` и реализовать его во всех посетителях. Поэтому Visitor подходит для относительно стабильного набора типов с часто добавляемыми операциями. Для маленькой задачи с единственной операцией отдельные посетители могут быть избыточны.

## Проверки

`VisitorTests` проверяет расчёт по смешанной коллекции, все типы элементов, точные границы обслуживания, третью операцию, неизменяемость результатов, отклонение неверных данных и арифметику без переполнения `int`. Проверки не требуют JUnit и завершаются ошибкой при нарушении условия.

## Выбор реализации

Для элементов я использую `record`, потому что модулю достаточно хранить данные без их изменения. Java автоматически создаёт конструктор, методы чтения, `equals`, `hashCode` и `toString`. В компактном конструкторе я проверяю название и числовые значения. Метод `accept` написан отдельно в каждом элементе: именно там вызывается нужный метод посетителя.

`long` в расчёте энергии нужен, чтобы произведение количества объектов на коэффициент не переполняло `int`. `List.of` создаёт неизменяемую коллекцию модулей, а `List.copyOf` защищает списки результатов от изменения извне.

Программа работает в консоли. Для демонстрации паттерна графический интерфейс и база данных не нужны.
