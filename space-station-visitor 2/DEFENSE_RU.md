# Подготовка к защите Visitor

## Рассказ на одну минуту

Я реализовал Visitor для модулей космической станции. Есть три типа элементов: жилой модуль, лаборатория и оранжерея. Они реализуют интерфейс StationModule с методом accept. Посетители рассчитывают энергопотребление, определяют необходимость обслуживания и формируют инвентарный отчёт.

Клиент хранит объекты в List<StationModule> и вызывает accept для каждого элемента. Элемент вызывает соответствующий метод посетителя, передавая себя. Благодаря double dispatch алгоритм определяется и типом модуля, и типом посетителя. Проверки типов не нужны.

Новая операция добавляется отдельным посетителем без изменения элементов. Третий посетитель InventoryReportVisitor показывает эту возможность. Цена подхода — при добавлении нового типа элемента нужно обновить интерфейс посетителя и все его реализации.

## Что уметь написать на бумаге

```java
interface StationModule {
    void accept(ModuleVisitor visitor);
}

interface ModuleVisitor {
    void visitHabitat(HabitatModule module);
    void visitLaboratory(LaboratoryModule module);
}

record HabitatModule(int residents) implements StationModule {
    public void accept(ModuleVisitor visitor) {
        visitor.visitHabitat(this);
    }
}

record LaboratoryModule(int activeExperiments) implements StationModule {
    public void accept(ModuleVisitor visitor) {
        visitor.visitLaboratory(this);
    }
}

class EnergyVisitor implements ModuleVisitor {
    long total;

    public void visitHabitat(HabitatModule module) {
        total += 20L + 5L * module.residents();
    }

    public void visitLaboratory(LaboratoryModule module) {
        total += 12L * module.activeExperiments();
    }
}
```

Это сокращённая схема для объяснения механизма; полный проект включает три элемента, три посетителя, валидацию и закрытое состояние результатов.

## Возможные вопросы

**Зачем нужен Visitor?** Чтобы добавлять разные операции над стабильным набором типов объектов, не помещая каждый новый алгоритм в классы этих объектов.

**Где double dispatch?** Сначала выбирается конкретный accept по реальному типу элемента. Затем внутри accept вызывается метод конкретного посетителя для этого типа элемента. Например: HabitatModule.accept → EnergyConsumptionVisitor.visitHabitat.

**Почему нужен accept?** В проекте нет общего метода `visit(StationModule)`. У посетителя есть методы для конкретных типов. Клиент знает элемент как `StationModule`, поэтому вызывает `accept`. В конкретном элементе тип `this` уже известен, и вызывается нужный метод посетителя. В варианте Visitor с перегруженными методами `visit(...)` выбор перегрузки тоже зависит от статического типа аргумента, а не от его типа во время выполнения.

**Что добавится для новой операции?** Новый класс посетителя с реализацией всех visit-методов и его подключение в клиенте. Элементы и ModuleVisitor остаются прежними.

**Что добавится для нового типа модуля?** Новый элемент, новый visit-метод интерфейса и реализация этого метода во всех посетителях.

**Почему Visitor — поведенческий паттерн?** Он организует выполнение операций и распределение ответственности между объектами.

**Какие принципы Clean Code применены?** Понятные имена; полиморфизм вместо проверок типов; одна ответственность на посетителя; инкапсуляция; расширение операций без изменения элементов. На защите покажите соответствующие участки кода, перечисленные в README.

**Как сохраняется инкапсуляция?** Модули неизменяемы, посетителям доступны только значения через accessors. Возвращаемые списки — неизменяемые копии. При этом посетители зависят от открытых данных элементов, что является компромиссом паттерна.

**Почему результат равен 124?** Жилой модуль: 20 + 4 × 5 = 40. Лаборатория: 3 × 12 = 36. Оранжерея: 6 × 8 = 48. Сумма 124 кВт·ч за сутки.

**Кому требуется обслуживание?** Orion: 35 дней ≥ 30. Eden: 7 дней ≥ 7. Kepler: 10 дней < 14, обслуживание пока не требуется.

**Почему создаётся новый посетитель для нового расчёта?** Посетители хранят накопленный результат. Повторный обход тем же объектом добавит значения повторно.

**Чем Visitor отличается от Strategy?** Strategy обычно подменяет один алгоритм, используемый контекстом. Visitor добавляет операцию сразу для разных типов элементов через набор типоспецифичных методов.


**Почему использован record?** Это краткая запись класса для хранения данных. Java создаёт приватные final-поля, конструктор и методы чтения. В моих модулях все компоненты — числа и неизменяемая строка, поэтому состояние модуля нельзя изменить после создания. Сам Visitor не требует records: обычные классы тоже подходят.

**Что делает List.copyOf?** Возвращает неизменяемый снимок списка. Внешний код не сможет добавить или удалить задачи внутри посетителя.

**Зачем Validation?** Чтобы не повторять одинаковые проверки в трёх конструкторах. Пустое название и отрицательные значения отклоняются сразу.

**Почему в формулах long?** Количество хранится в int, а коэффициент — в long. Поэтому умножение выполняется в long и не переполняет int при больших значениях.
